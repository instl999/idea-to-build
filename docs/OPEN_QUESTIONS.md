# 待确认问题

这些问题不能仅凭当前代码得出唯一答案。确认后应把结论写入相应权威文档，并从本文件移除或标记已解决。

## 产品需求

### Q-001：正式目标用户和成功指标是什么？

- 为什么需要确认：决定 onboarding、文档深度、默认流程和发布优先级。
- 当前代码表现：支持一般数字产品想法和 Codex 用户，但没有用户研究、使用数据或 KPI。
- 不同答案影响：个人开发者、产品团队或企业治理场景会需要不同协作、权限和可观测能力。

### Q-002：Codex-only 是永久产品边界还是 0.3.0 的阶段性收缩？

- 为什么需要确认：影响 SkillHub/OpenClaw 现有发布物、兼容声明和未来适配投资。
- 当前代码表现：README、Skill 和参考协议明确排除跨宿主支持。
- 不同答案影响：永久边界可简化契约；阶段性边界需要抽象宿主能力和独立安全测试。

## 业务规则

### Q-003：调度何时算 `COMPLETE`，如何进入 `RELEASE_READY`？

- 为什么需要确认：当前状态机含目标状态但没有 finalize 路径。
- 当前代码表现：`start` 设置 `ACTIVE`，wave 退休不更新完成状态；adapter 不记录已完成 task/current wave，也不强制依赖或 merge order。
- 不同答案影响：可能需要 adapter 持久化完成进度并阻断提前 wave/乱序 merge，或明确保留宿主流程/人工验收门禁。

### Q-004：研究评分阈值是否有实证依据？

- 为什么需要确认：评分直接影响采用/配置/扩展/自建建议。
- 当前代码表现：阈值和权重硬编码并有透明测试，但没有校准来源。
- 不同答案影响：若只是启发式，应强化提示；若要产品化，需要版本化研究与回测。

## 架构决策

### Q-005：是否允许引入开发期 lint/typecheck/coverage 依赖？

- 为什么需要确认：当前纯标准库约束与质量缺口之间存在取舍。
- 当前代码表现：CI 没有这些工具，贡献指南要求新增依赖先说明。
- 不同答案影响：允许开发依赖可提高静态质量；完全零依赖则需加强标准库检查和人工规范。

### Q-006：是否需要支持 monorepo 子目录作为生成项目根？

- 为什么需要确认：当前 `ensure_exact_git_root()` 明确拒绝父 Git 根。
- 当前代码表现：每个生成项目必须是独立精确 Git root。
- 不同答案影响：支持 monorepo 会重写安全边界、提交范围、worktree 和恢复逻辑。

### Q-007：生成项目运行时副本的升级策略是什么？

- 为什么需要确认：用户项目可能长期保留旧脚本，而安装 Hook 使用新插件运行时。
- 当前代码表现：初始化时复制脚本，没有升级命令或兼容矩阵。
- 不同答案影响：可选择固定快照、显式迁移器或版本绑定；每种方案影响可复现性和安全修复。

## 数据处理

### Q-008：状态、研究、日志、提示词和任务分支应保留多久？

- 为什么需要确认：这些内容可能含产品/组织信息并进入 Git 或模型服务。
- 当前代码表现：没有自动保留/删除策略；新生成项目的 `.gitignore` 默认忽略测试记录和 guardrail 日志，但既有项目、备份、强制添加与 Git 历史仍需单独治理。
- 不同答案影响：需要不同清理、备份、审计和用户提示机制。

### Q-009：JSON schema 是否需要成为公开、版本化接口？

- 为什么需要确认：外部工具或未来 UI 可能依赖 state/ledger/manifest。
- 当前代码表现：schema 仅由 Python 代码隐式且不完整地定义，版本为 1；研究输入和 `last_test.json` 也没有完整 schema/出处契约。
- 不同答案影响：公开 schema 增加兼容责任，但能改善验证和工具集成。

## 权限与安全

### Q-010：团队环境中谁有权执行人类核心确认？

- 为什么需要确认：当前只记录 `actor: human`，不验证身份或角色。
- 当前代码表现：精确命令/语句和流程边界防止 AI 代执行，但任何有终端权限的人可能运行。
- 不同答案影响：高治理场景可能需要签名、审批人、双人复核或外部身份系统。

### Q-011：GitHub 的分支保护、secret scanning 和 push protection 是否已启用？

- 为什么需要确认：仓库文档建议开启，但本地配置不能证明远端状态。
- 当前代码表现：CI 权限最小化，发布审计为启发式。
- 不同答案影响：未启用时发布误操作和 secret 风险更高，需要人工门禁或平台配置。

## 部署和运维

### Q-012：0.3.0 的正式版本、tag 和发布渠道是什么？

- 为什么需要确认：本地 manifest、`pyproject.toml` 和 changelog 已统一为 0.3.0，但最近确认的 tag 仍是 v0.2.0。
- 当前代码表现：当前工作树准备合并到 `main`；2026-08-06 的远端 heads/tags 只显示 `main`/`v0.2.0`，Plugins Directory 状态未知。
- 不同答案影响：若准备发布需同步元数据、tag、远端和安装验证；若仍是开发版应明确预发布标识。

### Q-013：最低支持 Codex 版本和 Hook/协作能力矩阵是什么？

- 为什么需要确认：宿主版本、rollout 和组织策略可能关闭关键能力。
- 当前代码表现：仅写“current Codex Desktop/CLI”，无机器可读最低版本。当前官方文档确认 CLI marketplace 管理、Desktop Plugins Directory 安装；本机 `codex.exe` 帮助因系统拒绝执行而无法验证。
- 不同答案影响：决定安装前检查、错误提示、测试矩阵和支持成本。

### Q-014：事故响应、备份和恢复目标由谁负责？

- 为什么需要确认：插件会操作 Git、worktree 和冻结契约，但没有远程运维服务。
- 当前代码表现：文档建议保留分支/证据并从已知 commit 恢复，没有 SLA/RPO/RTO。
- 不同答案影响：个人工具可保持手工流程；团队/企业可能需要正式 runbook 和责任人。

## 第三方服务

### Q-015：Host Web Search 的允许提供商和数据政策是什么？

- 为什么需要确认：研究查询会离开仓库，且价格/许可等事实需要实时网络。
- 当前代码表现：Skill 要求最小化/假名化，Python 不直接联网。
- 不同答案影响：可能限制可搜索数据、来源、保留、地区或要求禁用网络研究。

## 历史遗留

### Q-016：此前 SkillHub 发布物应保留、下架还是标记为不兼容？

- 为什么需要确认：当前仓库已经明确 Codex-only，但本地 Git 不能确认外部分发状态。
- 当前代码表现：通用 SkillHub 和 OpenClaw 明确不在支持边界。
- 不同答案影响：错误保留可能误导安装者；下架或迁移需要外部发布权限和沟通计划。

## 本次审查新增

### Q-017：所有专项命令是否必须服从同一阶段转换图？

- 为什么需要确认：`TRANSITIONS` 只约束手工 transition，研究、readiness、冻结、生成和调度路径直接写阶段；当前文档过去把它描述为统一状态机。
- 当前代码表现：部分专项路径有强前置条件，部分只校验数据后直接跳到目标阶段，phase history 也不完整。
- 不同答案影响：统一图会强化可审计性但可能改变既有 CLI 行为；保留专项门禁则需公开每条来源阶段和兼容契约。

### Q-018：测试门禁需要什么级别的执行证明？

- 为什么需要确认：Stop Hook 已校验项目 ID、runner 标记、声明命令、结果与快照，并阻止 Hook 可观察的直接写入；但有文件系统权限的外部进程仍可重算普通字段，无法提供密码学执行证明。
- 当前代码表现：`record-test` 真实执行命令且不经 shell；记录现在受 Hook 可见写路径保护并带 runner/project 元数据，但仍无签名或宿主回执。
- 不同答案影响：流程信任只需强化告警；安全门禁则需要受保护 runner、签名/nonce、宿主执行证据或不可伪造日志。

### Q-019：研究协议和 package 完整性应在哪一层强制？

- 为什么需要确认：Skill 要求丰富研究证据；package validator 已覆盖初始化复制的 10 个项目运行时及 Plugin 的完整 CLI/Hook/marketplace/记忆文件，但研究输入校验仍只覆盖协议子集。
- 当前代码表现：极简候选仍可得到 `BUILD_CUSTOM`；package 显式必需文件缺口已修复，但 22 份生成设计文档内容完整性和研究证据 schema 仍未被完整强制。
- 不同答案影响：严格 schema/清单会提高可靠性但可能拒绝旧项目；仅文档约束则必须降低“失败关闭/包完整”的承诺并增加人工检查。
