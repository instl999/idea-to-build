# 冻结核心变更控制

[English](CHANGE_CONTROL.md) | **简体中文**

## 原则

冻结核心在正常开发中不可变。0.3.0 刻意不提供解锁、重算 hash 或原地重冻命令。Hooks、Skills 和 AI 任务不得修改锁/核心或伪造人类批准。把 hash 更新成与不明修改一致会破坏证据，绝不是修复。

根智能体或子智能体属于可逆的 Codex 开发执行选择，刻意不写入冻结产品锁。只要文件所有权、验收、架构、隐私、安全和部署契约不变，切换执行策略不需要核心变更。

## 非核心变更

仍满足契约的实现细节应进入设计/live 文档与代码。记录决定和风险，运行核心校验与必需测试，更新 STATUS，再正常提交。

## 影响核心的请求

1. 停止依赖争议契约的实现。
2. 在 `docs/live/CHANGE_REQUESTS.md` 记录提出者、日期、原因、受影响需求/核心文件、隐私/安全/部署影响、迁移/回滚、替代方案和验收变化。
3. 保留证据：当前核心 hash、tag/commit、工作树状态、校验输出和相关决定；不要修改冻结文件。
4. 取得明确的产品、安全和技术评审。仅为掩盖失败而降低验收的变更必须拒绝。
5. 若批准新基线，在人类控制下创建全新生成项目，或单独初始化的精确 Git 仓库/分支。只复制已审查的可变事实/决定，重新起草五份核心契约，并重跑完整研究与就绪流程。
6. 人类审查完整新预览并亲自运行精确确认/冻结命令；保留旧基线/tag 用于回滚和审计。
7. 通过评审后的计划迁移实现，校验新旧引用、测试、数据迁移、回滚和发布说明。

不要在原冻结项目中静默替换旧锁。如果组织必须原地维护多基线，应先开发并审计专用的人类授权迁移工具；本版本不提供该能力。

## 紧急完整性失败

若没有批准请求却校验失败，应按潜在损坏处理：停止工作，保留副本/日志/Git 状态，确认写入者和范围，轮换可能泄露的凭据，在恢复分支从已知良好 commit 恢复并调查。绝不能对未知内容重算 hash 来“修好”事件。
